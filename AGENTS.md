# Project knowledge and working rules

## Goal and communication

Paperboy is a display service for ePaper and text displays (own firmware on ESPHome with deep sleep, ADR 0041; OpenDisplay is not supported by the service yet). Since v2 (ADR 0049) a page is a grid of widgets, and every widget comes from a plugin: a long-running program configured in `paperboy.yaml` that draws the widget in exactly the size of its cell. Paperboy composes the pages and delivers them according to a plan per device. Evolved from SolarAI's display service `displayd` (ADR 0028, 0029).

- Communicate with the user in German.
- Everything in the software is English: identifiers, comments, log messages, error messages, CLI help texts, commit messages and documentation (README, AGENTS.md, new ADRs) (ADR 0031). Paperboy must support multiple languages and number/date formats; the global `language` reaches the plugins with every request, and the built-in image texts (battery warning, stale bar, notices) follow it. Existing ADRs 0012–0030 stay German.
- Adapt changes in structure and naming to the existing code.
- For larger requests (e.g. removing features or options, multiple files/ADRs affected), briefly summarize before implementation (what changes, what stays, risks) and carry them out only after confirmation by the user.
- Paperboy does not import any SolarAI packages. Data sources are reached only by plugins (a SolarAI plugin talks to SolarAI over HTTP itself); Paperboy talks only to plugins, over stdin/stdout.

## Versioning and decisions

- Git repository `github.com/maehld/paperboy`, branch `main`. After **every completed work step** create a commit with an **English** commit message in the imperative (ADR 0031). Run the appropriate checks before committing.
- **Pull requests are always squash-merged**, so one PR becomes exactly one commit on `main` whose body keeps the PR commits as bullet points. The issue number goes at the end of the commit message: the subject ends with `[#<issue>]` and the message ends with `Closes #<issue>` before trailers such as `Co-authored-by`, e.g. `Reload configuration on change [#1]` (commit `8958866`).
- Document significant decisions as ADRs under `docs/adr/` (template `0000-vorlage.md`, maintain the index `docs/adr/README.md`). ADRs 0012–0030 originate from SolarAI (0030 applies to both); new ADRs from 0032. Do not rewrite existing ADRs, supersede them with new ones.
- `paperboy.yaml`, the local instance content (`pages/`, `plans/`, `plugins/`, the v1 leftovers `providers/` and `icons/`, `state/`), the old `paperboy.json`/`displayd.json`, `paperboy-data/`/`displayd-data/` and `.env` are excluded via `.gitignore` and must not be committed or deleted.

## Architecture

Go **1.27 or newer**. Dependencies: `golang.org/x/image` **v0.24.0** (ADR 0013), `go.yaml.in/yaml/v3` **v3.0.5** (ADR 0024, 0026) and `tinygo.org/x/bluetooth` **v0.16.0** only in the package `internal/opendisplay/odble` (ADR 0016; the Paperboy binary does not contain it). Further dependencies only with their own ADR.

## Essential rules for devices

- **No upload endpoints and no data API:** pages are composed from plugin widgets and selected by plans. A device without a plan, with a missing or broken page or a broken plan gets a notice page, never an error; a failing widget only marks its own cell.
- **Device API (ADR 0042):** plain HTTP status codes; `401` makes the firmware drop its key and register again by MAC, so a lost `state/devices.json` only costs the page cursor and the battery level. Image paths are relative; the device keeps the Paperboy URL it was configured with.

## Hardware findings

- **E1001** (MAC 44:1B:F6:85:AA:1C; findings below from the TRMNL firmware, 2026-10-17): battery voltage e.g. `4.08`, 4 gray levels look good. OpenDisplay: ID 0 = green button, 1 = the one to its left, 2 = the one left of that. ESPHome: buttons left→right GPIO5 = `previous`, GPIO4 = `next`, GPIO3 (green) = `home` (confirmed 2026-10-31 with firmware 0.4.0, which had the first two swapped), battery ADC GPIO1 ×2 with enable GPIO21; ESPHome's panel model is black and white only.
- **Sticky** (MAC B8:1F:3F:D8:6A:FC): ESPHome gray4 panel bands luma at 32/96/160 (map 0/85/170/255 into the bands); touch needs `swap_xy` + `mirror_x` + `mirror_y` with `rotation: 180`; power latch GPIO45/46 held through deep sleep; BQ27220 currents/capacities ×10.
- **Battery:** Sticky „Küche“ (“Kitchen”) 3.40 V after a long time without charging, E1001 „Wohnzimmer“ (“Living room”) 3.75 V; fluctuation approx. 0.02 V.
- **OpenDisplay firmware** (`cmd/odtest`): BLE under Windows on Sticky ODE46FD8 successful (reading configuration, test image 48 KB in approx. 31–33 s; not discoverable for a few seconds after disconnecting). Wi-Fi on reTerminal Sticky and E1001 successful (test image in native orientation). `-buttons` polls the 16-byte status block (`0x0044`) cyclically; Sticky (10.1.2.133): button on status byte 5, touch bytes 0–4. Byte 5 shows the last pressed button (ID 0 = top button, 1 = page up, 2 = page down) with **its own 4-bit counter per button**; short presses are often visible only in the counter → press = change of (ID, counter). Touch: contacts 1–5 = touched, 6 = released (coordinates remain); touch flags 0b111 (invert x/y, swap); coordinate range not yet calibrated.

## Planned work

Paperboy v2 (ADR 0049) replaced the data document (ADR 0024), the region model (ADR 0032), the block templates with their typography, formats and icons (ADR 0034, 0035, 0038, 0046), exec providers (ADR 0036) and text-line templates (ADR 0044) with plugins that provide widgets on a grid. The ADRs stay as history; the README describes only v2. The spike that led there is documented in `docs/spikes/plugin-fragments.md`. Existing installations migrate by hand (README); there is no migration code.

Still in place from v1: the device API (ADR 0042) with text displays (ADR 0044, 0045), plans (ADR 0025), configuration reload (ADR 0047), device status and dashboard (ADR 0039, 0040), firmware distribution (ADR 0043) and the battery warning (ADR 0020). ADR 0041's firmware compiles for `sticky`, `e1001` and `lcd2004` but is not yet flashed; the rollback test with a broken image is still open before `firmware.update: auto` is used on real devices. The calendar plugin has not yet run against the real iCloud.

Open: a page editor on top of `GET /api/plugins` and the grid, a SolarAI plugin (it talks to SolarAI over HTTP; SolarAI knows nothing about Paperboy), plans/delivery for OpenDisplay, data conditions in plans (`when.data`) and push delivery to text displays. `TestBatteryWarningFlow` fails on Linux (also on `main` before v2): the banner text covers the two-pixel bar of the 40×20 test display.

## Startup and checks

```powershell
go run ./cmd/paperboy -config . -listen :8090
go test ./...
go vet ./...
.\scripts\build.ps1             # paperboy, odtest and the plugins into bin/<os>-<arch>/
./scripts/package-plugins.sh dist  # plugin zip for the host platform
```

- Apply `gofmt` to changed Go files.
- **Windows Firewall blocks per binary path (confirmed 2026-10-22):** `go run` starts the server from a new `%LOCALAPPDATA%\go-build\<hash>\…\paperboy.exe` each time, so every build is a new program for the firewall. A dismissed prompt leaves a permanent **inbound Block** rule for exactly that build: displays on the LAN get "connection refused" or timeouts, while `127.0.0.1` (SolarAI) keeps working. Check with `Get-NetFirewallApplicationFilter | ? Program -like "*paperboy.exe"` and prefer a stable binary from `.\scripts\build.ps1` (`bin\<os>-<arch>\paperboy.exe`) that is allowed once, instead of `go run`.
- **UTF-8 on Windows:** Windows PowerShell 5 reads UTF-8 files as ANSI, so a `Get-Content … | Set-Content …` round-trip turns „Für“ into „FÃ¼r“. Edit files with the dedicated tools, or read and write them with `[System.IO.File]::ReadAllText`/`WriteAllText` and `UTF8Encoding($false)`; never pipe source files through `Get-Content`/`Set-Content`.
- Prefer tests for protocol behavior and state transitions.

Keep this document up to date with relevant architecture or behavior changes.
