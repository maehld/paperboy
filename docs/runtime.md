# Runtime

## Web UI

Paperboy serves its operator pages on the same address as the device API. They need no token (see [Security](#security)). The dashboard, the stats page and the downloads page poll themselves and update in place, so a tick does not reload the document ([ADR 0106](adr/0106-self-updating-pages-with-htmx.md)); without JavaScript they stay readable but stop updating.

### Dashboard

`GET /` redirects to `/ui`, a read-only overview of all devices ([ADR 0040](adr/0040-operator-dashboard.md)). Each card shows the status, the plan and its active rule, a preview of the last served page (the lines for text displays), last contact and a *Power* row with the charge state — `Charging`, `Connected` (on mains without a charge current) or `Discharging` — followed by the state of charge or, when the hardware has no percentage, the voltage; the battery warning adds `low` or `critical`. The raw battery reading (voltage, charge and current), the display type with the hardware, refresh, address and firmware sit in a collapsed *Details* block, a *Last charge* line names when the last charging episode ended and what it did (`2 h ago · 41 → 50 %`, the voltage pair on hardware without a percentage), and a *Runtime* line estimates how long the battery lasts (`~12 d`, below two days in hours) or says *still collecting* while the series has no measurable discharge yet; the tooltip of that line names the data behind it (`5 h of data`, `24 h of data · estimate in ~9 h`) and the note next to the value marks an estimate from less than a day of data as *early estimate*. Mains devices and hardware without a battery reading show no such row. *Signal* sends one device a beep or blink at its next sync ([ADR 0142](adr/0142-a-manual-alert-waits-for-the-next-sync.md)); the button is disabled while the device cannot take the request, and the line below it names the reason (`alert_methods`, a problem or no registration). A queued signal shows in *Details* with its expiry until the next sync. The last render or plan error is shown below the card as text. The page is a server-rendered Go template and needs no token. It polls itself every 30 seconds: the request is the page again and htmx morphs only the grid, so an opened *Details* block, the scroll position, the text selection and the loaded previews stay as they are; a hidden tab does not poll and refreshes as soon as it is visible again, and a served image carries the hash of its pixels so the browser keeps it until the page changes ([ADR 0106](adr/0106-self-updating-pages-with-htmx.md)). Rendered PNGs live in memory only, so after a restart a card omits `last_page_url` and uses the page preview or a placeholder. The header shows the running build: version (or `dev`), short commit with `+dirty` for local changes, and commit date from the VCS stamp; the Go toolchain is in the tooltip. Every page links Configuration in its header.

The *Last charge* line comes from the fuel gauge current, with the threshold of the *Power* row: an episode starts with the first sync above 20 mA and ends with the first one below it. Both ends keep the charge and voltage the hardware reported, and the state file keeps the episode, so a charge that ends while Paperboy is down closes at the next sync — with that sync's time and charge, not the real ones.

The *Runtime* estimate learns the discharge rate from the device instead of a model of the cell: Paperboy keeps one battery sample per hour (at most 168, a week) in the state file and fits a straight line through the series (least squares, so one wandering gauge value cannot decide the estimate). It follows the fuel gauge's remaining capacity (`mah`) first, then its percentage, then the voltage, each with the drop that counts as a discharge: 2 mAh, 1 point or 0.05 V. Below that drop, while the series rises and on hardware that reports no battery, the line says *still collecting*; the tooltip names the data and, while the rate makes that promise within two days, when an estimate can be expected (`24 h of data · estimate in ~9 h`). An estimate from less than a day of data is marked *early estimate*, a longer one as *estimated*, and a projection beyond a year says nothing. A charge clears the samples, so it does not look like a slow discharge; hardware without a fuel gauge uses the voltage down to an empty cell at 3.0 V.

### Stats

`/ui/stats` ([ADR 0104](adr/0104-runtime-stats-in-the-web-ui.md)) shows what Paperboy costs while it runs. It is server-rendered, polls itself every ten seconds and writes nothing; the tables are morphed in place, so the page keeps its scroll position ([ADR 0106](adr/0106-self-updating-pages-with-htmx.md)).

The first block is Paperboy itself: start time and uptime, goroutines, `GOMAXPROCS`, heap in use against the memory the runtime reserved, the live heap with its object count, the stack, the garbage collector (cycles, next target, last pause), the resident memory and the CPU time with the share of one core used since the previous view. CPU percentages compare with the previous view of the page, because a process only exposes its cumulative CPU time; the first view names the total and shows no percentage.

The plugin table has one row per plugin — the built-in one included. It names the state (running since, failing with the retry time, not running, built-in), program and version, PID, resident memory and CPU, the requests it answered with the failed ones and the last error, and two timings: *Answer* is how long the plugin took, *Wait* is how long a request waited for another request of the same plugin. The last columns are the widgets it keeps in the cache with their bytes. Memory and CPU come from the operating system and stay empty for the in-process plugin and on platforms that do not report them.

The widget cache follows: entries, images, bytes, stale entries, entries past their expiry, evictions and the age of the oldest entry, then one row per age range (under a minute, five minutes, an hour, a day, older) with entries, images and bytes. Below it Paperboy counts its own caches: rendered pages and notice pages with count, bytes and age, and the parsed page and plan files.

*Timings* lists named operations with count, last, average, p50, p95 and maximum: the sync as a whole, the configuration snapshot, the wait for the state lock, the plan values, plan selection, the page render split into waiting for plugins and PNG encoding, running a menu action, writing the state file, every page render and the text poll. Percentiles come from the last 256 samples of an operation. *Syncs and polls* finally has one row per device: its syncs with last, average, p95 and maximum duration, and the text polls separately, because a text display asks every second and would otherwise dominate the numbers.

### Plan preview

The **Plan preview** button at the foot of a device card opens `/ui/plan?device=<id>` ([ADR 0054](adr/0054-plan-preview-in-the-web-ui.md)), a read-only view of the plan of the device. It shows every rule with its time window, `on_refresh`, `refresh` and `alert` mode, the fallback, the rule that applies now (or at the time picked with `&at=YYYY-MM-DDTHH:MM`) and the next rule change. Each page is previewed for the display type of the device; pages the device would skip show the reason, broken pages their error. The view does not change the page cursor or the state of the device.

### Virtual display

The **Virtual display** button at the foot of a device card and the *virtual display* link in the plan view open `/ui/virtual?plan=<plan>&display=<type>` ([ADR 0091](adr/0091-virtual-display.md)). The page acts as a display of that type: it syncs like the firmware, shows the page the plan picks, pages with the buttons of the plan and opens the device menu. Optional URL parameters replace what a device file would decide: `refresh`, `menu` (5–60 s) and `power=mains|battery`. The URL is the only configuration, so a link is a display. The cursor and the menu live in memory and not in `state/devices/`, so no device is touched. *Reset* starts again at the first page. The picture comes from `/ui/virtual/pages/…` and `/ui/virtual/hints/…`, which serve the same PNG and QOI as the device routes but follow the UI password ([ADR 0096](adr/0096-a-password-for-the-operator-ui.md)): the browser has no device key ([ADR 0097](adr/0097-page-downloads-take-the-device-key.md)).

Paperboy resolves, selects and confirms actions like on a device, but never runs them: the result banner says *Simulated* and names the action. `←`/`→`/Enter and press-and-hold work, *Full screen* hides the chrome, and a debug line below the display names the active rule, the page, the refresh, the wake and the last error.

### Playground

`/ui/plugins` (linked from the dashboard) opens the page editor without a page. It offers image display types only ([ADR 0124](adr/0124-the-playground-shows-image-display-types.md)): text pages are edited under Configuration → Pages. A link with a text display type opens the first image type and names that page; an instance with text display types only says so. Pick a widget in the palette, or open the page without a widget and it starts with the built-in header. Paperboy draws the widget in its cell size on the chosen display type. The inspector shows its size, arguments and style. The snippet panel shows the finished cell, ready to copy into a page. Sizes are spans on a reference grid of 6 × 8 cells (`?grid=` changes it), and plugins declare their sizes as spans of that grid.

`GET /api/plugins` lists every plugin with its widgets, the sizes they are designed for, their arguments and the config keys of the plugin. A single widget is available as `GET /api/widget/<plugin>/<widget>?display=<type>` with `span=3x2` (and `grid=6x8`) or `width`/`height` in pixels, and arguments as `arg.<name>=<value>` (JSON values keep their type, e.g. `arg.days=3`). It answers a PNG, and for a failing widget the notice a page would show, with the reason in `X-Widget-Error`. A text display type answers `400`: its pages are built from values, not widgets ([ADR 0125](adr/0125-remove-the-text-widget-path.md)).

### Configuration

`/ui/editor` is one overview with a sub-tab per object type (`?tab=pages|plans|devices|displays`, default pages). Each tab has one card with its count, a filter field and its new-object button in the header. The button asks for the name in a dialog (a page also chooses the display type) and opens the editor of the new object. A row opens its object: the name is a link, and a click on the row follows it. Rename and Delete live in the editor and name the references ([ADR 0073](adr/0073-edit-creates-and-deletes.md), [0079](adr/0079-rename-config-items.md), [0084](adr/0084-the-overview-links.md)). Every editor shows the same action bar `← <list>` · object · status · Rename · Delete · Reload · Save ([ADR 0076](adr/0076-one-stylesheet-and-one-navigation.md)). A save sends the model with the hash it read, so a file changed on disk answers `409` and asks for a reload. Paperboy keeps the last ten old versions under `state/editor/`.

#### Page editor

The pages tab lists one row per page ([ADR 0110](adr/0110-pages-serve-their-kind-and-name-variants.md)). A row shows the page file when it exists, else its first variant, with kind, grid or row count, title and parse error. The variants column names the other files as chips with their label; the tooltip holds the path, the display types the page sends to the file and any error. The row and the chips open exactly that file. A variant that no display type names is italic and stays a candidate in the *Variants* select. A page without a page file shows its name in red, and its variants are read-only until the operator creates the page file with *New page*. The *New page* dialog asks for the kind, and for a text page for its character grid. `/ui/editor/page?name=<page>&file=<label>` opens one page file, with `display=<type>` as the preview type and `&new=1` for a page file that does not exist yet ([ADR 0068](adr/0068-page-editor-ui.md)). The editor names the open file behind the page name (`page countdown - hochkant`) and edits the title, the grid and the style; a variant has no title. A text page is a character grid of boxes ([ADR 0118](adr/0118-text-boxes-and-overflow.md)). The right inspector edits only the selected box: `at`, `span`, value or literal text, label, a unit choice, a scale select, align and overflow, with a full-width *Delete cell* button. The board draws a box per cell; drag moves it and an edge or corner resizes it. Scrolling boxes stay static, and the board note names the step. The palette lists the declared values and a *Text* entry; click one and then a slot, or drag a value onto the board. Text pages hide the style in points, show *Stale values* instead of *Stale widgets*, and expose the page's `overflow`. Without JavaScript the boxes render as read-only fields and save nothing. For the selected cell of an image page the editor sets the span, the position, the arguments and the style.

A single *Variants* table lists every configured display type with the files of the page that fit it. The select changes the file of a type, and its tooltip says why a type is not served. The display type links to its preview with the open file, or to the file that serves it. A `variants` entry whose display type is no longer configured keeps its row; `— none —` drops the entry and the file stays. *Create variant…* asks for a display type and a file label, starting with the first type that no file serves. It writes a variant that starts from the type: its kind and character grid come from the display and never from the open file. A variant is a child page: it shows the title of its page file read-only, and a *Variant* block links the page and lists the display types the page sends to the file. The block has two actions. *Rename…* gives the file a new label and rewrites every entry that names the old one. *Reassign…* moves the file to another page with a page file, and its entries go with it. The table stays with the page file, because it owns the variants. The editor never renders another file in place of the open one.

Click a widget and then a free cell, or drag it from the palette. A placed box is moved with the pointer (it stays where it was grabbed) or by its position. Resize it by the handles on its right edge, bottom edge and corner; a size or position that would overlap another box is not applied ([ADR 0085](adr/0085-moving-and-resizing-widgets.md)). A live draft preview shows the result.

The board is the rendered draft with the cell boxes on top ([ADR 0074](adr/0074-editor-board-shows-the-preview.md)): an image as its background, the text lines one character per slot in a dark green LCD module with the vendored pixel font ([ADR 0116](adr/0116-a-pixel-font-for-text-previews.md)). A *Cells* switch hides the overlay (remembered per browser, forced on while placing), and a "rendering…" hint covers the debounce.

Nothing is written before *Save*. A file that does not parse is listed with its error and opens read-only, because the API takes a model, not text. *Delete* removes the one file the editor shows after naming the plans that use the page ([ADR 0073](adr/0073-edit-creates-and-deletes.md)). *Rename* moves `pages/<page>.yaml` and every variant file as one set, keeps the `variants` map ([ADR 0079](adr/0079-rename-config-items.md), [0113](adr/0113-a-page-rename-moves-its-variants.md)). A taken target file refuses the whole rename with `409`, and every move is preflighted before the first rename. A variant has no page rename in its bar; *Rename…* in its *Variant* block changes the label. A variant whose page file is missing stays read-only and is not linked from the pages list.

#### Plan editor

`/ui/editor/plan?name=<plan>` edits a plan ([ADR 0069](adr/0069-plan-editor-ui.md)). A missing file opens as a new plan that the first save writes. The editor edits rules in their order: name, time window (`from`/`to` as times of day, days as checkboxes), pages in their order with `on_refresh`, `refresh` and `alert`, and the fallback. It also edits the actions the device menu offers, built from the actions of the plugins with their arguments and confirmation.

The editor marks rules that an earlier rule always overrides. It names pages that the own devices of the plan would skip, and links each device to its `/ui/plan` preview and to its device page. *Delete* removes the plan after naming the devices that use it. *Rename* moves the file ([ADR 0079](adr/0079-rename-config-items.md)).

#### Device editor

The devices tab lists the files under `devices/` with display type, MAC, address and plan, and creates new ones in a dialog. Hardware that registered with an unknown MAC appears below them as unclaimed, with its hardware, firmware, address and first and last contact. *Claim* asks first, then opens a new device file with the MAC prefilled; *Forget* deletes its state file ([ADR 0080](adr/0080-device-state-per-mac.md)).

`/ui/editor/device?id=<id>` edits one ([ADR 0070](adr/0070-devices-in-their-own-files.md)): display type, MAC address, plan chosen from the plan files, `refresh`, the device menu (`actions`, `menu_show_duration`, `touch`), the alert methods (`alert_methods`, default silent; [ADR 0132](adr/0132-alert-methods-per-device.md)), the power source, the rotation (a device override, [ADR 0102](adr/0102-rotate-pages-onto-the-panel.md)), the firmware hold and the battery thresholds. It links the plan preview of the device and the current file text. The editor writes only the device file, so a plan assignment never touches `paperboy.yaml`. A new device file needs a display type and a MAC address.

*Delete* removes the file; the device stops syncing until a file with its MAC exists again ([ADR 0073](adr/0073-edit-creates-and-deletes.md)), and its state waits under the MAC. *Rename* moves only the file; the state stays with the MAC, so the page cursor, battery reading and menu survive ([ADR 0079](adr/0079-rename-config-items.md), [0080](adr/0080-device-state-per-mac.md)).

#### Display type editor

The displays tab lists the files under `displays/` with kind, size, `ppi` or `charset`, gray levels and power, and creates new types in a dialog. `/ui/editor/display?name=<name>` edits one ([ADR 0071](adr/0071-display-types-in-files-of-their-own.md)) with the fields of its kind, the rotation of an image display ([ADR 0102](adr/0102-rotate-pages-onto-the-panel.md)), the physical size computed from `ppi`, the pages that name a variant for it and the devices that reference it, and the current file text.

The `ppi` field has a helper. It converts the diagonal of the panel in inches or one side of its active area in millimetres into `ppi` from the pixel size in the form. It says so when the two disagree, because an inch diagonal is usually rounded. *Rename* moves only the file ([ADR 0079](adr/0079-rename-config-items.md), [0110](adr/0110-pages-serve-their-kind-and-name-variants.md)). *Delete* removes the file after naming the pages and devices that reference it ([ADR 0073](adr/0073-edit-creates-and-deletes.md)).

## Device API

`POST /api/device/register` with `{"mac", "hardware", "firmware"}` (optionally `power` and `touch`) returns `{"key", "device"}` for a configured MAC (an existing key is kept) and `403` otherwise ([ADR 0042](adr/0042-device-protocol.md), [ADR 0064](adr/0064-device-protocol-v4.md)). The `403` carries `code` and `expires_in` until the operator entered the code the panel shows. The *Pair* button in the device editor posts the code to `POST /api/state/devices/{mac}/pair`, a UI route. The next register then takes the key ([ADR 0109](adr/0109-pair-a-display.md)). Every wake sends one `POST /api/device/sync` with `Authorization: Bearer <key>`:

- `reason`: `timer`, `button`, `touch`, `powercycle`, `menu` or `result`.
- `events`: buttons by role `next`, `previous`, `home`, optionally with `hold_ms`; touches with `x`/`y`. Each event has a monotonically increasing `id`, and Paperboy ignores a repeated ID.
- `shown`: the hash on the panel.
- `battery`: `volts` is required, `percent`, `mah` and `ma` are optional. `ma` is the current from the fuel gauge, positive while charging. `charging` is the charger's own state (the Sticky reads the BQ25616's `STAT` pin) and cross-checks the gauge.
- `rssi`, `power` and `log` entries.

The answer names the image (`image.path` relative to the Paperboy URL, `image.hash`) and the deep-sleep time `refresh_s`. It also names `listen_s` (0 after a timer wake, 20 s after input) and `sleep` (`false` for mains devices, [ADR 0051](adr/0051-power-source-refresh-policy.md)). It names the server `time` in Unix seconds and `firmware` (an update offer, otherwise `null`). The firmware sets its clock from `time`, because the certificate check of an `https://` URL needs it ([ADR 0108](adr/0108-verify-the-tls-certificate.md)). `rotation` is the effective page rotation in degrees clockwise (0, 90, 180 or 270), omitted when it is 0; the firmware applies it before painting and to touches ([ADR 0102](adr/0102-rotate-pages-onto-the-panel.md)). `beep` and `blink` are `true` when a plan rule or a manual signal wants the device to signal; the device uses the method it has, after the paint ([ADR 0131](adr/0131-a-plan-rule-alerts-the-device.md), [0135](adr/0142-a-manual-alert-waits-for-the-next-sync.md)). `wake` (`{reason, after_s}`) is a one-shot wake for the menu deadline or an action result; otherwise it is absent. An unknown key gets `401`, and the device registers again. An invalid body gets `400`.

A device whose file has a `Problem` answers with `503` and the reason, never with `401` ([ADR 0079](adr/0079-rename-config-items.md)).

**Text displays** ([ADR 0044](adr/0044-text-displays-on-the-device-api.md)): register and sync like ePaper displays, but the sync answers `"image": null` and a `text` object, and `listen_s` is always 0. They run on mains power and never sleep. Between syncs they poll `GET /api/device/text?shown=<hash>` with their key every `refresh_s`, which the plan decides ([ADR 0045](adr/0045-text-poll-interval-from-the-plan.md); the firmware syncs at most once a minute and uses one minute until its first sync). The answer carries `lines`, `hash`, the `scrolls` boxes and `scroll_changed`; unchanged text gets `204`. The firmware keeps a scroll offset while `scroll_changed` is false and animates the boxes on the server's `step_ms` ([ADR 0118](adr/0118-text-boxes-and-overflow.md)). The legacy `scroll` rows stay for older images ([ADR 0092](adr/0092-scrolling-text-lines.md)). The poll renders the page the cursor points to without advancing it and writes nothing to the state file of the device. It updates the shown content in memory for `/api/devices` and the dashboard. An image display gets `409`. Paperboy word-wraps notices (no plan, broken page, critical battery) into the lines.

**Buttons**: events apply in order before rendering. `next` = next page, `previous` = one page back (wrapping), a long `next`/`previous` = first page of the active rule, `home` = the device menu ([ADR 0057](adr/0057-plugin-actions-from-the-plan.md), [ADR 0067](adr/0067-buttons-and-the-menu.md), see [Actions](content.md#actions)). A short `home` always opens the menu, also when the plan offers no actions; then it is an empty banner. With the menu open, `next`/`previous` move the selection and `home` confirms; a long `home` closes the menu and keeps the page. A rule change starts at the first page; the rule's `on_refresh` decides what a timed refresh shows ([ADR 0130](adr/0130-what-a-plan-refresh-does.md)). Touches operate the device menu when it is open (the Sticky sends taps, [ADR 0064](adr/0064-device-protocol-v4.md), issue #54); outside a menu, Paperboy only logs them. The server decides at 700 ms whether a press was long; the firmware only measures and reports `hold_ms`.

## Operation

### Intervals

`defaults.refresh` (at least 1 minute) or the `refresh` of the device applies; the `refresh` of a device may go down to 1 s. A plan rule may override it (down to `1s`). `refresh_s` in the sync answer is the sleep until the next sync: a timer sync lands on the grid of its interval, so ten minutes give :00, :10 and :20 ([ADR 0129](adr/0129-align-timer-syncs.md)). The dashboard and the `late` check name that sleep. The reported interval never goes below the floor of the power source ([ADR 0051](adr/0051-power-source-refresh-policy.md)). Battery devices keep one minute or the `min_refresh` of the display type if that is longer. Mains devices go down to `min_refresh`: by default `1s` for text and `10s` for image displays. When the composed image does not change, the display does not redraw.

### Power source

`power: auto|battery|mains` on the display type, overridable per device; default `auto` ([ADR 0051](adr/0051-power-source-refresh-policy.md)). The firmware reports `power` (`battery` or `mains`) in register and sync: the Sticky measures USB power on GPIO9, the E1001 cannot detect it and reports `battery`, and text displays report `mains`. `auto` uses the last report (`reported_power` in `/api/devices`, next to the effective `power`) and behaves as `battery` until the device reports one. Text displays with older firmware therefore fall back to a one-minute floor until you update them or set `power: mains`. The sync answers `sleep: false` for mains devices: the ePaper firmware then stays awake with Wi-Fi up and syncs again after `refresh_s` instead of deep sleeping. A change of the reported source or of the charger state gets one `power changed` line in the journal (with `power`, `charger`, voltage and current), so the log tells the story instead of repeating the reading on every sync.

### Battery warning

The warning is fed by `battery.volts` of the sync ([ADR 0020](adr/0020-akkuwarnung-trmnl.md)). With `battery` in `defaults` or on a device, every page below `warn_volts` gets the bar *Battery low – please charge* (*Akku schwach – bitte laden*). Below `critical_volts` a full-screen image *Battery almost empty* (*Akku fast leer*) appears instead, and buttons then do not page. A level ends only `hysteresis_volts` above its threshold. Without `battery` there is no warning. All texts use the configured `language`.

### Firmware updates

Put OTA images into `firmware/<hardware>-v<version>.bin` of the instance (`firmware/esphome/build.ps1 -Hardware sticky -Instance <dir>` does it). Paperboy offers the highest version in the sync as `{"version", "path", "md5"}`. It compares the version part by part as numbers; a `firmware.version` pin narrows it to exactly that image ([ADR 0060](adr/0060-download-from-releases.md)). It offers an update when all of these conditions hold ([ADR 0043](adr/0043-firmware-distribution.md)):

- `firmware.update` is `auto`.
- The device has no `firmware: hold`.
- The reported version differs (a lower file is a rollback).
- The battery reading is at least `min_battery_volts` and not at warning level (text displays run on mains power and skip the battery condition).
- The version has not failed three times on that device.

A sync that still reports the old version after an offer counts as a failure. A changed image (new MD5) or clearing `firmware_failures` in the state file `state/devices/<MAC>.json` allows new attempts. Paperboy serves images at `GET /firmware/<file>` without a token; it ignores other file names and lists them in the log and on the dashboard. `GET /api/devices` adds `firmware_available` and `firmware_status` (`current`, `offered`, `available`, `failed`, `held`, `none`). Test the rollback with a broken image before you use `update: auto`.

### Device logs

The sync carries firmware log entries (`level`, `message`, optional `source`, `time` and `id`). Paperboy writes one line per entry with device, level, source and age. An entry with a `time` or `id` that a repeated sync delivers again is logged only once.

### Device list

`GET /api/devices` shows every configured device without keys: registration, hardware, firmware, battery voltage (and `battery_percent`, `battery_mah`, `battery_ma` and `battery_charging` from hardware that knows them; `battery_ma` is positive while charging), signal strength, wake reason and last sync. It also shows what the device is showing ([ADR 0039](adr/0039-device-status.md)). The fields are `last_page`, `last_page_kind` (`page`, `notice` or `battery`), `last_page_hash`, `last_page_url` and `last_refresh` (text displays: `last_text` instead of `last_page_url`). The last render or plan error is in `last_error`, and a derived `status` is `ok`, `late`, `never` or `unregistered`. `late` means the last sync is more than twice the reported refresh old; devices deep-sleep, so an idle device is not an offline one.

## Security

Devices are admitted by allow list and use their own key. The device API answers with plain HTTP status codes (`400`, `401`, `403`). The dashboard, the editor, the preview, the virtual display, `GET /api/devices`, `GET /api/plugins` and the page and plan API need no token, so keep Paperboy in a trusted network. Whoever reaches `/ui` can change the pages and plans. Only plugins named in `paperboy.yaml` run, so the configuration file is executable content.
